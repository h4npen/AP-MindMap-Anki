🧠 脳に刻む合言葉：

『 ACIDのAはAtomicity（原子性）！Availability（可用性）は部外者！ 』

1. なぜそうなるのか？（日常のたとえ話：送金処理の厳格ルール（途中で失敗したら全戻し、矛盾なし、他人と混ざらない、停電でも消えない））

トランザクション処理の信頼性を保証する4大原則が ACID（アシッド）特性 です。

• A（Atomicity / 原子性）: 100円送金するとき、「Aさんの残高引落」と「Bさんの残高加算」は両方成功するか、両方失敗（ロールバック）するかのどちらかしかない。
• C（Consistency / 一貫性）: データベースのルール（残高はマイナスにならない等）を常に保つ。
• I（Isolation / 独立性・隔離性）: 複数の人が同時に送金しても、混ざらずに1人ずつ順番に処理したのと同じ結果になる。
• D（Durability / 耐久性）: 「送金完了」と出たら、直後にデータセンターが落雷で停電してもデータは絶対に消えない。

「可用性（Availability）」は、情報セキュリティの3要素（CIA: 機密性・完全性・可用性）やRASIS（信頼性指標）に出てくる言葉で、ACIDには含まれません！

0. 一枚で：『ネットワーク分散DBで、全サイトの更新整合性を保つのが「2相コミット」！』

🧠 脳に刻む合言葉：

『 第1相で「全員の準備完了」を確認！第2相で「一斉コミット（またはアボート）」！ 』

1. なぜそうなるのか？（日常のたとえ話：ロケットの発射シークエンス（「全エンジン準備完了」「了解、オールグリーン、一斉点火！」））

東京のサーバと大阪のサーバにあるデータベースを同時に更新するとき、東京だけ成功して大阪がネット切断で失敗したら、データが矛盾して大惨事になります。

この分散トランザクションを「All or Nothing（原子性）」で成功させるのが 2相コミット（Two-Phase Commit Protocol） です！

2つのフェーズ（相）：

1. 第1相（準備フェーズ）: - 調整者（親）が参加者（子）全員に「コミットの準備はできたか？」と尋ねる。 - 参加者はログを書き出し、準備ができたら「Ready（OK）」と返事する。 2. 第2相（コミットフェーズ）: - 全員からOKが届いた場合: 調整者は「全員コミットせよ！」と号令をかける。 - 1人でもNGまたは無応答だった場合: 調整者は「全員ロールバック（取り消し）せよ！」と号令をかけ、全員を元の状態に戻す。

この2段階を踏むことで、ネットワークをまたいだ分散環境でもデータの矛盾を完全に防ぎます！

2. 選択肢のひっかけポイント ＆ 判定理由

• イ: チェックポイント → メモリ上の更新データをディスクに書き出し、障害復旧の起点にする技術。
• ウ: 排他制御 → ロックなどを用いてデータの同時更新を防ぐ技術。
• エ: ロールフォワード → 障害発生時にバックアップとログを用いて最新状態まで前進復帰させる技術。
• 「分散DBで問い合わせてからコミット」と来たら、反射的に 「2相コミット」 一択です！

3. 本番で絶対に迷わない「6ステップ完全解法」

今回の問題 192.168.0.0/23 と 192.168.2.0/23 を例に、一切省略せずにステップ順で解いてみましょう。

ステップ①：数字を2進数（0と1）に翻訳する

• 192 の作り方: 128 + 64 = 192 ➔ 左の2つの箱を使う ➔ 11000000
• 168 の作り方: 128 + 32 + 8 = 168 ➔ その3つの箱を使う ➔ 10101000
• 0 の作り方: どの箱も使わない ➔ 00000000
• 2 の作り方: 2の箱だけ使う ➔ 00000010

これを4ブロック並べると、2つのアドレスの「真の姿」が見えます。

192.168.0.0 ➔ 11000000 . 10101000 . 00000000 . 00000000
192.168.2.0 ➔ 11000000 . 10101000 . 00000010 . 00000000

ステップ②：「/23」の意味を確認して境界線を引く

「/23」はサブネットマスクであり、「左から23個目までがグループの共通の看板（ネットワーク部）ですよ」 という意味です。 1ブロックは8個なので、第1(8)＋第2(8)＝16。第3ブロックの7個目が「23個目」です。 
192.168.0.0/23 : 11000000 . 10101000 . 0000000 | 0 . 00000000
192.168.2.0/23 : 11000000 . 10101000 . 0000001 | 0 . 00000000
                                                ↑
                                            ここが23ビット目

ステップ③：左から見て「お揃いの限界」を探す（集約の神髄！）

2つのアドレスを上から見比べて、左から何文字目まで完全に一致しているか探します。 
192.168.0.0 : 11000000 . 10101000 . 0 0 0 0 0 0 [0] 0 . 00000000
192.168.2.0 : 11000000 . 10101000 . 0 0 0 0 0 0 [1] 0 . 00000000
                                    └────┬─────┘  │
                           左から22個目まで一致！  23個目は「0」と「1」で不一致！
• 23個目の数字は「0」と「1」で食い違っています。
• しかし、その直前である 「左から22個目」までは完全に一致 しています！
• したがって、2つを1つにまとめる新しい境界線は 「 /22 」 に決定します！

ステップ④：境界線の右側を全ゼロにリセットする

集約後の代表ネットワークアドレスを作るときは、「境界線の右側（ホスト部）をすべて 0 にリセットする」 という絶対ルールがあります。 
【左から22個目まで（お揃い部分）】 : 11000000 . 10101000 . 000000
【残り10個（すべて 0 にリセット）】 :                         00 . 00000000
────────────────────────────────────────────────────────────────────────────
【集約後のビット列】               : 11000000 . 10101000 . 00000000 . 00000000

ステップ⑤：10進数に戻す

8個ずつ区切って、普段の数字に戻します。
• 1番目: 11000000 ➔ 128 + 64 ＝ 192
• 2番目: 10101000 ➔ 128 + 32 + 8 ＝ 168
• 3番目: 00000000 ➔ どの箱もゼロ ＝ 0
• 4番目: 00000000 ➔ どの箱もゼロ ＝ 0

これをつなげると 192.168.0.0。
新しく決めたマスク「/22」を後ろにつけて、192.168.0.0/22 の完成です！

『 コネクション識別は4点セット！送信元・宛先の「IP＋ポート」！ 』

1. なぜそうなるのか？（日常のたとえ話：会社の代表電話と内線番号（どちらの会社の誰から、どちらの会社の誰宛てか特定する））

パソコンで複数のブラウザタブを開き、同じWebサーバ（例：YahooやGoogle）に同時にアクセスしても、なぜ画面の表示が混ざらないのでしょうか？

それは、OSがすべての通信を 「4つの情報の組み合わせ（4-tuple）」 で完全に識別しているからです。

1. 送信元IPアドレス: 自分のPCの住所
2. 送信元TCPポート番号: 自分のブラウザのタブごとに振られた一時ポート（例: 51234）
3. 宛先IPアドレス: 相手サーバの住所
4. 宛先TCPポート番号: 相手サーバの窓口番号（例: Webなら80や443）

この4つが1つでも違えば、別の通信（別のコネクション）として正しく仕分けされます。MACアドレスはLAN内の隣の機器（ルータ）に渡るたびに書き換わってしまうため、エンドツーエンドのコネクション識別には使えません。

2. 選択肢のひっかけポイント ＆ 判定理由

• ア・ウ・エ: MACアドレスが含まれている
→ 【即消去！】 MACアドレス（データリンク層/L2）はルータを超えるたびに次のホップのものに書き換わります。相手サーバと結ぶ「TCPコネクション」の識別には一切関与しません！
• イ: 宛先IP，宛先ポート，送信元IP，送信元ポート 【正解！】
→ ネットワーク層のIPとトランスポート層のポート番号、両者の送信元・宛先の計4点セットが正解です。
